# Streaming keyword spotting with INT8 inference

A 23,756-parameter DS-CNN keyword spotter for Google Speech Commands v2 (12 classes), quantised
to INT8 and run on a live-style audio stream in pure Python: incremental NumPy MFCC features,
ONNX Runtime inference, posterior smoothing and detection, with latency, memory and detection
errors measured under documented conditions. No C++, no microphone capture.

All numbers below are generated from committed scripts that write to `results/`
(`python -m tools.results_table` builds this table). Every results file records the date, git
commit, CPU, core count, OS, Python and package versions, ORT thread settings and the command.
Timings are **Python on the host CPU** (Intel Core i7-13650HX, 20 logical cores, Windows 11,
Python 3.12, onnxruntime 1.31.1), not device or accelerator latency.

## Reading the results

- **INT8 is slower than FP32 here, by about 8.6x** (optimised, 1 thread, inference p50). The
  ORT per-operator profile (`results/ort_profile.json`, from `tools/profile_ort.py`) shows the
  time is almost all in `QLinearConv`: the stem and 1x1 convolutions, not the depthwise ones, and
  not the extra quantise/dequantise nodes. FP32 `Conv` kernels on this CPU are already very fast
  for a model this small, and the INT8 kernels are not. I did not test why the INT8 convolution
  kernels are slow (for example the weight layout or the requantisation step), so that is an
  observation, not an explanation of the cause. INT8 does save size (37,589 B vs 94,637 B) and
  loses 0.04 accuracy points, but on a desktop-class CPU with a tiny model it buys no speed. An
  MCU without a fast FP32 path, or an NPU with INT8 MACs, is where INT8 would be expected to pay
  off; that is not measured here.
- **Incremental features help, modestly end to end.** The feature stage drops from p95 0.279 ms
  (baseline, recompute 49 frames) to 0.025 ms (optimised). Per-hop p95 for INT8 goes from
  0.946 ms to 0.663 ms, because inference, not features, dominates at p95.
- **Allocations.** Baseline allocates about 251,570 bytes per hop on average (Python side,
  tracemalloc high-water mark); optimised about 9,736. Optimised is not zero: the NumPy
  `rfft` result and a few small temporaries are allocated each frame. ORT's native allocations
  are not visible to tracemalloc and are excluded.
- **Garbage collector.** Disabling it made no measurable difference to hop p95/p99 on the
  stable run; only the max (single worst hop) moved, and not consistently.
- **Deadline.** Across 50 benchmark runs (10 configurations x 5 repetitions) there was exactly
  one hop over 20 ms: a 24.5 ms hop in one baseline FP32 1-thread repetition (the table shows
  the median across repetitions, so it reads 0). Single worst hops in the other runs ranged
  from 4.9 ms to 17.7 ms; these are rare OS-scheduling-type spikes, which I did not investigate.
- **Detection quality is poor.** On the 1-hour test stream the chosen point misses 46.7 % of
  keywords (INT8) with 15 false accepts/hour, far worse than the 92.78 % clip accuracy. The
  window diagnostic (`results/stream_window_diagnostic.json`) points at the model on noisy,
  unseen-noise audio, not at the streaming code: streaming features and predictions equal the
  offline ones exactly. I did not retrain.

## Reproduce

```
python -m venv .venv && .venv/Scripts/activate        # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python -m train.run_all                                # download data, train, export, quantise, evaluate
python -m tools.stream_parity                          # streaming vs batch features, predictions
python -m tools.make_streams --split val --minutes 20
python -m tools.make_streams --split test --minutes 60
python -m tools.sweep_threshold                        # validation sweep, picks the operating point
python -m tools.eval_stream                            # test stream, final detection numbers
python -m tools.bench                                  # latency matrix (about 1 hour)
python -m tools.profile_ort                            # per-operator profile
python -m tools.results_table                          # regenerate docs/RESULTS.md and this table
```

Everything except training (`train.run_all`, about 10 minutes on a 20-thread laptop CPU) can be
rerun from a fresh clone once `models/` exists. Checks: `ruff check .`, `mypy`, `pytest`.
Single streaming run:

```
python -m kws.stream --model models/dscnn_int8.onnx --wav data/streams/test.wav --threshold 0.93 \
    --smooth 4 --infer-every 5 --threads 1 --mode optimised --detections out.csv --timings out.json
```

## Layout

`features/` shared MFCC definition (config, mel/DCT matrices, NumPy reference) - `train/` data,
DS-CNN, training, export, quantisation - `kws/` ring buffers, streaming MFCC, ORT wrapper,
detector, timing stats, stream CLI - `tools/` stream generation, scoring, sweep, benchmark,
profile, results table - `results/` committed outputs - `docs/` DESIGN, EXPLAIN_BACK, PROGRESS,
RESULTS.

## Limitations and what did not help

- **Benchmark conditions matter.** My first benchmark runs, on battery with the Balanced power
  plan, drifted by up to 2x within one configuration (`results/unpinned/`,
  `results/battery_run/`). Pinning the process to one core did not fix that; plugging the laptop
  in and interleaving repetitions across configurations did (spread across the 5 repetitions is
  a few percent or less). The reported results are from that run. The 1-thread runs are pinned
  to logical CPU 2, which I assumed is a performance core; I did not verify it.
- All-cores runs let ORT choose its thread count; they are not pinned.
- One machine, one OS, one run of the whole matrix (5 repetitions each); no confidence
  intervals beyond the min/max across repetitions stored in the results files.
- Stream metrics: 15 false accepts in one hour is a small count with wide uncertainty. The
  operating point rests on 3 false accepts in a 20-minute validation stream. Stream noise comes
  from two held-out files reused over an hour, word boundaries are an energy heuristic, and 30 %
  of stream words are unknown words, more than a natural mix.
- Quantisation: no fallback was needed (-0.04 points), so QAT, per-tensor and Entropy/Percentile
  calibration were not tried (the one attempt made is in `results/quantization_attempts.json`).
- Disabling the garbage collector and using more threads did not help latency here; more
  threads made INT8 inference faster (0.625 -> 0.251 ms) but FP32 slightly slower.
